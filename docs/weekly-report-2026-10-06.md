# 基于 Agent 信息流控制的最小数据、权限管理（ZBN）

## 一、问题与定义

Agent 常被授予整个目录、邮箱或外部服务的访问能力，但单个任务通常只需要其中一部分。提示注入、错误规划或子 Agent 委派可能使这些权限被用于无关操作。现有难点是：任务描述不完整，执行路径会变化，而“与任务相关”也不等于“完成任务必需”。

**最小权限**：在明确的任务目标、完成标准和执行环境下，授予足以完成任务、且无法继续缩减的操作权限。权限应描述主体、资源、操作、参数范围、有效期及委派范围。例如，“总结指定论文并生成邮件草稿”需要论文读取、指定输出位置写入及草稿创建权限；邮件发送、读取其他邮件不在该任务范围内。如果使用云端模型，还需单独允许论文内容发送到指定模型服务。

最小权限可能有多个可行集合，不应假定大模型一次就能求出唯一答案。工程目标是得到可执行、可解释、尽量小的权限集合。一次执行用过的权限只是该执行路径的记录，其中可能包含冗余操作，不能直接作为最小权限的标准。

**最小数据**：任务允许引入的数据范围，可按文件、邮件、记录或字段限定。第一阶段在数据首次进入该任务上下文前检查，包括文件读取、工具返回和历史记忆加载；访问新对象仍需重新检查。它解决访问入口问题，后续传递、改写和外发由信息流策略控制。

## 二、方案及初稿调整

初稿方向可行，建议采用“任务权限建议—策略校验—运行时拦截—信息流审计”的方案。需要调整两点：大模型生成的结果是候选策略；执行中的扩权必须满足明确规则，不能由执行 Agent 自行判断相关后直接放行。

1. **生成任务策略。** 根据可信任务描述、资源元数据和预设任务模板，生成结构化权限建议，列出允许的数据、工具操作、参数、输出位置、接收方和期限。策略生成阶段不先读取全部用户数据。候选策略经独立规则校验，并受系统权限上限约束。
2. **在操作发生前执行校验。** 文件读取、工具执行、网络发送和子 Agent 创建均经过统一的策略执行层。通过受限文件接口、沙箱和网络出口限制防止绕过；不能仅检查工具名称或 shell 命令字符串。默认拒绝未授权操作，保留拒绝原因和证据。
3. **按阶段申请临时权限。** 新资源请求需要说明对应任务步骤、资源范围和用途。符合预设扩权规则的请求可自动获得短期权限；超出规则的请求暂停该操作，必要时进行一次具体授权。任务结束撤销权限。子 Agent 只获得与子任务有关的父权限子集，禁止委派扩大权限。
4. **控制数据接收方。** 对数据来源及派生结果保留标签，在进入模型服务、工具或子 Agent 前检查接收方。读取权限与外发权限分别定义。摘要和改写先采用保守的可能依赖标签；去除敏感字段或解除标签需经过独立、明确的处理规则。

整个工作目录授权可作为受控开发任务的初始范围，但不能覆盖邮箱、订票等个人助手场景。备份主要解决误删后的恢复，不能消除读取和泄露风险；密钥应由工具执行后端按调用注入，避免进入模型上下文。

## 三、相关论文与局限

下表区分论文的保护范围与针对本项目的设计判断，不将未研究的问题视为已证实的漏洞。

| 论文 | 方向与核心机制 | 局限及对本项目的启示 |
| --- | --- | --- |
| [IsolateGPT，NDSS 2025](https://www.ndss-symposium.org/wp-content/uploads/2025-1131-paper.pdf) | Hub 管理相互隔离的应用与 LLM 上下文，应用协作经中介接口和权限管理。 | 明确不保护单个应用内部的提示注入；主要限制跨应用影响。隔离并不能自动确定任务最小权限。论文性能评估自动批准权限请求，未反映实际授权负担。 |
| [ACE，NDSS 2026](https://www.ndss-symposium.org/wp-content/uploads/2026-s352-paper.pdf) | 先用可信信息生成抽象计划，再绑定具体应用；通过静态信息流分析和受控执行器验证、执行计划。论文也展示了针对 IsolateGPT 的规划及执行攻击。 | 验证依赖预设安全标签、应用等级及受限语言。对临时改变计划的开放式任务，需要额外规划与验证机制（设计推论）。验证策略合规不等于证明策略最小。 |
| [SAGA，NDSS 2026](https://www.ndss-symposium.org/wp-content/uploads/2026-s869-paper.pdf) | Provider 管理 Agent 身份和联系策略，以令牌限制通信对象、期限及请求次数，提供协议层安全分析。 | 联系策略仍需用户定义；令牌期限与性能之间存在权衡。通信认证不能推出内容与任务相关，也不能保证授权接收方不会泄露数据（保护范围分析）。 |

这些工作的价值在于提供隔离、验证和认证边界。对本项目而言，仍需解决三个问题：怎样从任务得到必要权限，怎样处理执行中的合法变化，怎样在数据改写后控制传播。尤其要区分“策略被正确执行”与“策略本身足够小”。

## 四、本周实现与验证

本周完成了信息流追踪原型，支持两种采集方式：

- **受控运行：** 在隔离工作目录内执行真实 Codex 任务，结合系统调用采集、客户端事件和模型请求网关，记录文件读取、模型请求、工具调用及显式子 Agent 委派。模型上游响应和本地工具回执分别作为接收证据。
- **桌面聊天：** 监听本地 Thread 日志，记录工具参数、返回和消息；结合 Windows 进程采样，自动输出调用树与系统进程树。显式父 Thread 字段用于连接子 Agent。

结果默认保存为 JSON/TXT，网页展示可选；支持持续刷新、原始日志保留和证据校验。改写传播已采用可能依赖标签：模型或 Agent 接触某来源后，后续输出及工具输入保留该来源候选。

验证结果：43 项自动化测试通过；真实受控任务成功完成，执行期间产生 31 次刷新，证据完整性校验通过。另一次任务因模型服务报错失败，已保留为不完整运行。

当前仍有边界：桌面日志不能证明内核实际读取或模型服务接收；共享桌面进程尚未归属到具体 Thread，轮询可能遗漏短命进程；改写标签会产生过度归因，未实现精确语义来源、文件版本传播和完整原生子 Agent 关联。因此，本周成果应表述为“可审计的信息流追踪原型”，完整追踪和权限强制执行仍在后续阶段。

## 五、下一阶段

先选择论文总结、邮件草稿、订单查询三类任务，定义完成标准和必要资源，由任务模板给出可复核的权限基线。在现有追踪器上接入文件与工具调用前的策略校验，实现首次数据访问限制、子 Agent 权限收缩和任务结束撤权，再扩展到网络出口的数据标签检查。

项目已有模型网关的目标主机白名单及内容标记拦截原型，但尚未覆盖通用命令、工具与子 Agent 权限。验证应同时记录任务成功率、无关数据访问量、越权放行率、合法操作误拦率及授权次数；使用提示注入、嵌套委派和改写外发案例检查能否绕过执行边界。

本阶段的研究重点是把任务约束转换成可执行的资源权限，并用真实执行证据校准策略范围。大模型负责提出建议，权限执行层负责约束实际行为。
