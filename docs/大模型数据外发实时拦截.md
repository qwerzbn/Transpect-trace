### 旁路 TLS 解密的可行性结论

需要区分三种路线：

| 路线 | 取得 Prompt 明文 | 能否单独实现发送前阻断 | 当前判断 |
|---|---|---|---|
| 只镜像流量，不取得端点会话密钥 | 正常的现代 TLS 无法通用解密 | 否 | 不作为实现路线 |
| 端点导出或提取会话密钥，再解密捕获流量 | 可以，前提是拿到对应连接的密钥并完成协议重组 | 否；需要另外在发送路径上暂存和判定 | 可作为审计、实验对照；本轮未实现官方二进制的密钥提取 |
| 加密前取得完整请求／消息并同步判定 | 可以，需适配客户端发送路径 | 可以，前提是被检查内容尚未发送且所有重试路径都受控 | 固定版本 HTTP EncodedJsonBody 与 WSS response.create 已有 Native 实验验证；未承诺其他路径 |

TLS 1.3 的会话流量密钥不能从被动抓到的握手、证书和密文中通用恢复。前向保密连接也不能仅靠服务器长期证书私钥还原历史会话。导出端点会话密钥是另一种能力，不应称为“旁路破解 TLS”。

即使已经能解密，纯镜像旁路仍没有暂停发送的位置。发现敏感内容后关闭连接可能发生在敏感字节已离开终端之后，不能满足“数据离开企业边界前识别并阻断”。加入 WFP 等发送暂存机制后，方案已经包含发送路径上的主动控制，而且仍需解决完整消息、并发连接、分片、重试和超时处理。

### 当前安装版本的实测

- 二进制：Windows 桌面应用附带的 `codex-cli 0.162.0-alpha.17.2`。
- SHA-256：`d13914ced6c7af174d8d638db938284231227312104b06a25e9608c632a7daec`。
- 使用原二进制、独立 `CODEX_HOME`、假数据 Prompt、无账号的自定义模型提供方。客户端直接连接本地 TLS 测试源站，源站不向任何上游转发。
- 测试证书只通过该子进程的 `CODEX_CA_CERTIFICATE` 信任，不安装系统证书。清除继承的代理和 API Key 配置，关闭测试进程的插件同步。
- HTTPS POST 和 WSS `response.create` 均完成，Codex 退出码均为 0，受测连接协商 `TLSv1.3 / TLS_AES_256_GCM_SHA384`。
- 设置可写路径 `SSLKEYLOGFILE` 后，两个受测路径均未创建客户端密钥日志，密钥条目为 0。二进制中包含 keylog 字符串并不能证明该功能已经在模型连接上启用。
- 在测试源站的原始 socket 接收位置保存 TLS 密文，再用**测试源站独立持有的会话密钥**离线解密。HTTPS 正文和经解掩码的 WebSocket 消息均恢复出假数据标记。这个对照证明捕获流和离线解密步骤有效；真实外部模型服务的密钥不在终端监管方手中。
- WSS 会先发送不含用户标记的预热请求，再发送实际用户请求。不能把预热连接等同于实际 Prompt 外发。

边界：这一 TLS 实验本身是本地 HTTPS 源站、子进程自定义 CA 的传输测试，不是对生产账号全部流量的覆盖证明。HTTP 的自定义 CA 路径使用 rustls；不能据此断言所有默认 HTTP 路径都使用相同 TLS 后端。后续独立 Native 实验验证了运行时插桩和局部发送前门控；仍未验证进程内密钥提取、真实模型流量解密和 HTTP/2 全部路径。

复现：

```powershell
uv run python scripts/probe_codex_tls.py
```

脚本默认在 `runs/codex-tls-feasibility/<随机ID>/` 保存二进制版本与哈希、独立配置、捕获的 TLS 字节流、测试源站会话密钥及 `summary.json`。`all_probes_validated` 只有在两个协议均完成、源站收到标记、离线解密也恢复出标记时才为真；握手失败不能被误判为密钥导出不可用。

已完成的完整实验：`runs/codex-tls-feasibility/installed-20261014-verified/summary.json`，其中 `all_probes_validated = true`。此前的证书失败和 WSS 握手修复运行仅用于调试，不作为结论依据。

### 调整后的 Codex 无代理方案

```text
Codex 准备完整 HTTP 请求或 WebSocket 消息
  → 本地 DLP 同步判定（通过 IPC，不转发模型流量）
  → 允许：由 Codex 原有连接完成压缩、编码、TLS 和发送
  → 拒绝：不调用发送路径，返回明确的策略错误并记录判定

ETW 证据与关联
  → 进程链、文件访问、网络事件与请求内容匹配
  → 派生来源关系采用 High / Medium / Low / Unknown
  → 不提供字节级污点证明；不决定正文检测是否执行
```

当前选择官方磁盘文件不修改、运行时插桩。固定版本的 HTTP 正文准备与 WSS 序列化入口已经完成 Frida 定位、安全错误路径验证及 Native 迁移；运行时通过语言无关 Named Pipe 同步判定。单纯包装 CLI 输入不够，因为工具返回和自动拼接上下文会随后进入模型请求。WSS 仅认证 response.create，不承诺完整 streaming。raw/multipart 附件、daemon 和其他网络出口仍未覆盖。

已检查同版本开源代码中的两个候选位置：

1. HTTP：`codex-rs/http-client/src/transport.rs` 的 `ReqwestTransport::send`。在 `req.prepare_body_for_send()` 前检查完整逻辑正文，覆盖需要检查的 JSON／字节／文件内容；不能等请求已执行后再分析。
2. WSS：`codex-rs/codex-api/src/endpoint/responses_websocket.rs` 的 `send_websocket_request`。在 `ws_stream.send(Message::Text(...))` 前检查完整序列化请求；同时梳理其他消息发送入口，不能把这一函数当作整个客户端的全部网络出口。

策略服务复用了 marker 判定与 `policy.decision` 审计结构，并加入初步凭据规则和登记文本匹配；仍不是通用个人信息和企业代码分类器。每个已覆盖入口的实际消息、后续工具结果、重试及 HTTP 回退均重新检查；放行一个 PID 或一条 TLS 连接不代表放行后续所有请求。默认请求拒绝，也支持经验证的会话阻断和显式终止，不自动升级杀进程。

Windows ETW 仅用于 Process lineage、File access evidence、Network evidence 和 Source correlation。采集与关联代码已实现，但当前账户启动会话返回权限错误 5，因此真实采集未通过验收，来源保持 Unknown。WFP 不会自动获得 rustls 的 Prompt 明文，本阶段没有实施全系统外联限制或防绕过。

已完成局部验收：正常正文放行；假敏感 Prompt 和 Agent 实际读取后的工具结果拒绝；受测敏感正文在源站零字节；受测 WSS→HTTP 回退和策略服务失联、超时、错 ID、畸形回复拒绝。仍需补充有权限的 ETW 实采、附件/扩展协议覆盖及长期压力验证。源站仅用于测试判据，不进入真实运行的连接路径。

## 问题

员工使用 Claude Code、Codex 这类编码代理时，代理会读取本地源码、配置和凭据，再通过模型 API 发往外部。现有做法多数是调用结束后查日志。请求已经离开本机，查到了也拦不住。

只看客户端自己的日志不够。日志可以由代理省略，TLS 上看到的是密文，系统调用只能看到“读过哪个文件、连了哪个地址”，看不到这段内容是否进了模型请求。要拦截，必须在模型 API 被转发之前同时具备三样东西：模型请求明文、端侧文件和进程行为、敏感数据从文件到请求的对应关系。

## 历史方案：Gateway（不符合新的无代理约束）

在编码代理和模型服务之间放一个本地 Gateway。代理只把模型流量发给 Gateway。Gateway 看到请求明文后先判定，允许才转发到上游。端侧同时记录进程实际做了什么，用来证明敏感数据从哪里来，以及有没有绕过 Gateway。

1. 采集分成四路，不把其中一路当成全部事实。
   - 客户端事件：Codex、Claude 的工具调用和会话日志。
   - Gateway：模型请求、响应和流式分片的明文。这是 LLM Sink。
   - strace：整个进程树进入内核的 exec、fork、文件、网络和 FD 操作。这是“发生过”的底账，静态链接程序也覆盖。
   - Frida Gadget：用 `LD_PRELOAD` 进入动态链接进程，补充函数参数、最多 4 KiB 的文件读写摘要，以及 `open`、`connect`、`execve` 的调用栈。它不占 ptrace，所以可以和 strace 同时运行。

2. 用内容把 Source、进程和 LLM Sink 连起来。
   - Source 是工作区里的文件。实验数据使用 `TRANSPECT_MARKER_*` 标记，并保存文件哈希。
   - Process 是读这些文件、发起工具调用的代理进程及其子进程，用 PID、工具调用标识和时间对齐。
   - LLM Sink 是 Gateway 记下的模型请求正文。标记或足够长的文件片段原样出现在请求里，就记成一条已解析的 Source → 模型请求信息流。

3. 判定放在 Gateway 转发之前，不放在运行结束后。
   - 允许的范围来自当前任务：可以读取的数据类别，以及允许到达的模型上游。
   - 请求正文里的敏感数据不在任务允许范围内，或上游不在允许列表内，Gateway 拒绝转发，并把判定和原始请求留在同一次运行的证据里。
   - 不经过 Gateway 的外联只由 strace 记录并标成缺口。这一阶段不在内核里做阻断。

Frida 只解释已经注入成功的进程。静态链接的 `codex-native`、清掉 `LD_PRELOAD` 的进程，以及直接发系统调用的代码，仍以 strace 为准。模型正文以 Gateway 为准，不在进程里解 TLS。

## 对原方案的修改

原第 1 步写成“抓取客户端流量”。客户端到模型服务的流量是 TLS，旁路抓包看不到 Prompt 和文件内容。改为由本地 Gateway 终止这一跳，在转发前取得明文。

原第 2 步把信息流写成采集当时就完成的关联。当前实现是运行结束后，用标记和内容哈希把工作区文件对应到模型请求。进程和行为已经能按 PID、工具调用和请求标识对齐。实时阻断还不能依赖这份事后关联，Gateway 做判定时只能使用当时已经看到的请求正文和任务策略。

原第 3 步用“目标域名”做授权。代理进程实际连接的是本地 Gateway，域名判断会把所有模型调用看成同一个地址。授权对象改成两件事：请求里携带的数据类型是否为任务所需，以及 Gateway 将要转发的模型上游是否被允许。

原方案没有区分端侧观测和端侧阻断。strace 与 Frida 负责证明行为，阻断只发生在 Gateway 转发之前。

## 历史实现进展

证据层之外，Gateway 已增加用于可重复安全测试的精确 marker 策略。策略把已知测试 marker 映射到源文件路径，并配置任务允许的源路径和模型上游。请求命中越权源文件或未授权上游时，Gateway 在建立上游请求前记录 `policy.decision` 和 `model.request.blocked`，返回 HTTP 403。

确定性集成测试使用进程内 Mock 上游计数器，验证被拒请求的上游调用次数为 0；同时覆盖正常请求放行和未授权上游拒绝。攻击 fixture 位于 `tests/fixtures/exfiltration/`。

系统层改为 strace 与 Frida Gadget 同时采集。Gadget 17.18.0 固定进 Codex、Claude 两个 Agent 镜像，构建时校验 SHA-256，以脚本模式随 `LD_PRELOAD` 加载，自己把 JSONL 写到 `raw/frida/`。外部注入已去掉：strace 占着 ptrace 时再 attach，会失败在 `target failed to mmap a region for the loader`。脚本只对普通文件读写保留最多 4 KiB 摘要，调用栈只加在 `open`、`connect`、`execve` 上，避免和 strace 互相卡住。

质量报告分开写出两边都看到的进程、只有 strace 的进程、只有 Frida 的进程。缺少 Frida 加载记录时，整轮不能算完成。Gateway 继续记录模型协议明文。运行结束后用标记和文件片段建立 Source 到模型请求的信息流。

9 月 24 日用真实 Codex 和 DeepSeek 跑通一轮，运行 `0fdb22d0-9c01-4e5c-977a-9b62280f9976`，质量状态为 `complete`。

- Gateway 记录 3 次模型请求，3 次都有对应的网络证据。
- 客户端完成 1 次工具调用。
- strace 覆盖 91 个进程、10683 条系统调用。
- Frida 在 11 个进程中加载成功，其中 10 个同时出现在 strace 里；其余进程列为 `strace_only_pids`，PID 20 列为 `frida_only_pids`。
- 1 条标记信息流已解析，假数据标记从工作区文件对应到了模型请求。
- 容器正常退出，没有注入崩溃。

同日的容器检查里，`cat` 同时留下 strace 和 Frida 记录并正常退出；Node 拉起的 shell 打印结果后正常退出。

## 历史实现的能力缺口

- 当前实时策略只支持预先登记的精确 marker 与源路径映射，不是通用敏感数据分类器。
- 运行结束后的内容关联仍用于完整证据恢复；实时判定不使用事后生成的信息流。
- 尚未覆盖 Base64、压缩、分片或语义改写后的敏感内容。
- 绕过 Gateway 的外联只有记录，没有阻断。
- 当前环境是 Windows 上的 Docker Desktop，没有加 eBPF。
