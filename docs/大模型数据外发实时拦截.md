# 大模型数据外发实时拦截

## 问题

员工使用 Claude Code、Codex 这类编码代理时，代理会读取本地源码、配置和凭据，再通过模型 API 发往外部。现有做法多数是调用结束后查日志。请求已经离开本机，查到了也拦不住。

只看客户端自己的日志不够。日志可以由代理省略，TLS 上看到的是密文，系统调用只能看到“读过哪个文件、连了哪个地址”，看不到这段内容是否进了模型请求。要拦截，必须在模型 API 被转发之前同时具备三样东西：模型请求明文、端侧文件和进程行为、敏感数据从文件到请求的对应关系。

## 方案

在编码代理和模型服务之间放一个本地 Gateway。代理只把模型流量发给 Gateway。Gateway 看到请求明文后先判定，允许才转发到上游。端侧同时记录进程实际做了什么，用来证明敏感数据从哪里来，以及有没有绕过 Gateway。

1. 采集分成四路，不把其中一路当成全部事实。
   - 客户端事件：Codex、Claude 的工具调用和会话日志。
   - Gateway：模型请求、响应和流式分片的明文。这是 LLM Sink。
   - strace：整个进程树进入内核的 exec、fork、文件、网络和 FD 操作。这是“发生过”的底账，静态链接程序也覆盖。
   - Frida Gadget：用 `LD_PRELOAD` 进入动态链接进程，补充函数参数、最多 4 KiB 的文件读写摘要，以及 `open`、`connect`、`execve` 的调用栈。它不占 ptrace，所以可以和 strace 同时运行。

2. 用内容把 Source、进程和 LLM Sink 连起来。
   - Source 是工作区里的文件。实验数据使用 `TRANSPECT_MARKER_*` 标记，并保存文件哈希。
   - Process 是读这些文件、发起工具调用的代理进程及其子进程，用 PID、工具调用标识和时间对齐。
   - LLM Sink 是 Gateway 记下的模型请求正文。标记或足够长的文件片段原样出现在请求里，就记成一条已解析的 Source → 模型请求信息流。

3. 判定放在 Gateway 转发之前，不放在运行结束后。
   - 允许的范围来自当前任务：可以读取的数据类别，以及允许到达的模型上游。
   - 请求正文里的敏感数据不在任务允许范围内，或上游不在允许列表内，Gateway 拒绝转发，并把判定和原始请求留在同一次运行的证据里。
   - 不经过 Gateway 的外联只由 strace 记录并标成缺口。这一阶段不在内核里做阻断。

Frida 只解释已经注入成功的进程。静态链接的 `codex-native`、清掉 `LD_PRELOAD` 的进程，以及直接发系统调用的代码，仍以 strace 为准。模型正文以 Gateway 为准，不在进程里解 TLS。

## 对原方案的修改

原第 1 步写成“抓取客户端流量”。客户端到模型服务的流量是 TLS，旁路抓包看不到 Prompt 和文件内容。改为由本地 Gateway 终止这一跳，在转发前取得明文。

原第 2 步把信息流写成采集当时就完成的关联。当前实现是运行结束后，用标记和内容哈希把工作区文件对应到模型请求。进程和行为已经能按 PID、工具调用和请求标识对齐。实时阻断还不能依赖这份事后关联，Gateway 做判定时只能使用当时已经看到的请求正文和任务策略。

原第 3 步用“目标域名”做授权。代理进程实际连接的是本地 Gateway，域名判断会把所有模型调用看成同一个地址。授权对象改成两件事：请求里携带的数据类型是否为任务所需，以及 Gateway 将要转发的模型上游是否被允许。

原方案没有区分端侧观测和端侧阻断。strace 与 Frida 负责证明行为，阻断只发生在 Gateway 转发之前。

## 本周完成

证据层之外，Gateway 已增加用于可重复安全测试的精确 marker 策略。策略把已知测试 marker 映射到源文件路径，并配置任务允许的源路径和模型上游。请求命中越权源文件或未授权上游时，Gateway 在建立上游请求前记录 `policy.decision` 和 `model.request.blocked`，返回 HTTP 403。

确定性集成测试使用进程内 Mock 上游计数器，验证被拒请求的上游调用次数为 0；同时覆盖正常请求放行和未授权上游拒绝。攻击 fixture 位于 `tests/fixtures/exfiltration/`。

系统层改为 strace 与 Frida Gadget 同时采集。Gadget 17.18.0 固定进 Codex、Claude 两个 Agent 镜像，构建时校验 SHA-256，以脚本模式随 `LD_PRELOAD` 加载，自己把 JSONL 写到 `raw/frida/`。外部注入已去掉：strace 占着 ptrace 时再 attach，会失败在 `target failed to mmap a region for the loader`。脚本只对普通文件读写保留最多 4 KiB 摘要，调用栈只加在 `open`、`connect`、`execve` 上，避免和 strace 互相卡住。

质量报告分开写出两边都看到的进程、只有 strace 的进程、只有 Frida 的进程。缺少 Frida 加载记录时，整轮不能算完成。Gateway 继续记录模型协议明文。运行结束后用标记和文件片段建立 Source 到模型请求的信息流。

9 月 24 日用真实 Codex 和 DeepSeek 跑通一轮，运行 `0fdb22d0-9c01-4e5c-977a-9b62280f9976`，质量状态为 `complete`。

- Gateway 记录 3 次模型请求，3 次都有对应的网络证据。
- 客户端完成 1 次工具调用。
- strace 覆盖 91 个进程、10683 条系统调用。
- Frida 在 11 个进程中加载成功，其中 10 个同时出现在 strace 里；其余进程列为 `strace_only_pids`，PID 20 列为 `frida_only_pids`。
- 1 条标记信息流已解析，假数据标记从工作区文件对应到了模型请求。
- 容器正常退出，没有注入崩溃。

同日的容器检查里，`cat` 同时留下 strace 和 Frida 记录并正常退出；Node 拉起的 shell 打印结果后正常退出。

## 尚未完成

- 当前实时策略只支持预先登记的精确 marker 与源路径映射，不是通用敏感数据分类器。
- 运行结束后的内容关联仍用于完整证据恢复；实时判定不使用事后生成的信息流。
- 尚未覆盖 Base64、压缩、分片或语义改写后的敏感内容。
- 绕过 Gateway 的外联只有记录，没有阻断。
- 当前环境是 Windows 上的 Docker Desktop，没有加 eBPF。
