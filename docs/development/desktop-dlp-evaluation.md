# 桌面端 DLP 内容识别评测（本地离线判定）

本评测只调用本地内容识别引擎，**不启动 Codex 桌面端，也不验证源站零字节**。实际发送前门控的本机实测另见 [Hook 门控记录](codex-hook-gate.md)，与本文分开验收。公开语料是合成或半合成 PII；文件夹具也是脚本生成的假密钥、假员工记录和假内部文档。样本文本不写入报告，也不发送给云端分类器。公开语料使用未登记企业记录和文档的基础策略，主要检验规则、校验、上下文及熵分析；只有另列的合成夹具登记了 EDM 与文档/源码指纹。因此公开语料表中的比例不能称为四层完整策略的检出率。

**引擎判定与门控动作分开报。** 报告 `1.2` 对每套语料同时给出 `decisions`（引擎判定）和 `gate_policy_actions`（部署策略实际会做的动作）。引擎报告全部证据，门控只对其中一部分动作：`CODE_STRUCTURE` 与 `ENTROPY_TOKEN` 默认仅记录不拦，依据见 [Hook 门控记录](codex-hook-gate.md)。只看 `decisions` 会把拦截比例说高。

前三套语料在调规则期间读过，属**开发诊断数据**。第四套是检测器冻结后才第一次读取的留出集，报告里以 `role: holdout` 标记，`development_corpora` / `holdout_corpora` 两个字段显式区分。它的脱敏副本用**发布方自带的 `masked_text`**，不是我们自己替换生成的，因此误报诊断不受我们脱敏方式的影响。留出仍**不等于**盲测标注集：实体标注不是策略动作，也没有独立标注者给出期望判定。

语料首次运行时下载到 `runs/desktop-dlp-datasets/`，之后按上述 SHA-256 核验；哈希不符即停止。DuckDB 固定为 `2.0.0`，运行依赖见项目锁文件。全量命令：

```powershell
uv run --no-sync --with duckdb==2.0.0 python scripts/evaluate_desktop_dlp_datasets.py --per-dataset 0
```

生成的详细报告在 `runs/desktop-dlp-datasets/report.json`。默认命令读取三套固定文件的全部 13,000 行；若要快速回归，可显式传入 `--per-dataset 500`，以种子 `2026-11-04` 和行 ID 的哈希在每套语料中固定抽样。默认运行不再以 500 行结果覆盖全量报告。上述两个中文文件分别是发布方标注的正式文本和带噪声聊天子集，不能合并成一个未分层结果。下载文件在进入缓存前、复用缓存时都必须通过固定大小和 SHA-256 核验。

## 结果与口径

引擎判定（`BLOCK / REVIEW / ALLOW`）与门控动作分列。门控拒绝率按 `REVIEW` 与 `BLOCK` 都拒绝计算。

| 语料 | 引擎 B / R / A | 门控 B / R / A | 门控拒绝率 | 判定 P95 |
| --- | ---: | ---: | ---: | ---: |
| Gretel 英文 | 1,154 / 595 / 3,251 | 1,154 / 579 / 3,267 | 34.66% | 0.212 ms |
| 中文正式文本 | 2,652 / 1,292 / 1,056 | 2,652 / 1,292 / 1,056 | 78.88% | 0.068 ms |
| 中文聊天文本 | 628 / 1,149 / 1,223 | 628 / 1,149 / 1,223 | 59.23% | 0.048 ms |
| **ai4privacy 英文留出** | 360 / 2,409 / 14,277 | 360 / 986 / 15,700 | **7.90%** | 0.301 ms |

脱敏副本（误报诊断）：

| 语料 | 引擎 B / R / A | 门控 B / R / A | 门控拒绝率 |
| --- | ---: | ---: | ---: |
| Gretel 英文 | 8 / 17 / 4,975 | 8 / 4 / 4,988 | 0.24% |
| 中文正式文本 | 0 / 0 / 5,000 | 0 / 0 / 5,000 | 0.00% |
| 中文聊天文本 | 0 / 0 / 3,000 | 0 / 0 / 3,000 | 0.00% |
| **ai4privacy 英文留出**（发布方 `masked_text`） | 238 / 1,532 / 15,276 | 238 / 25 / 16,783 | **1.54%** |

留出集上门控对原文拒绝 7.90%，对发布方脱敏副本拒绝 1.54%。副本上剩下的拒绝已逐条查过来源：发布方**没有标注**的 IMEI 和保单号仍留在 `masked_text` 里，例如 15 位、以 `36` 开头且 Luhn 通过的串——它在格式上与 Diners Club 卡号无法区分（IMEI 校验位本身就是 Luhn）。因此这 1.54% 不能当作干净真阴性上的误报率，`masked_text` 也不是干净的负样本集。副本上 1,505 条仅命中 `ENTROPY_TOKEN` 的行（加密货币地址等）在门控策略下不拦，这正是把引擎判定和门控动作分开报的原因。

按既定策略，门控遇到 `REVIEW` 即拒绝。本评测不证明门控已经部署；部署侧的实测见 [Hook 门控记录](codex-hook-gate.md)。语料含姓名、邮箱、电话等强弱不同的实体，不能把每个 `ALLOW` 都算作漏检，也不能把上表的拒绝比例称为准确率或召回率。前三套语料的脱敏副本由我们替换标注实体生成，留出集用发布方自带的 `masked_text`；两种方式下未标注的敏感内容都可能残留，因此这只是**误报诊断**，不是经人工核验的误报率。耗时为一次实测，会随机器负载变化，且仅测内容引擎，不含采集、加密落盘、IPC 和发送。报告 `1.2` 显式标记 `blind_holdout=false`、`policy_truth_available_for_public_corpora=false`、`live_enforcement_verified=false`，夹具行使用 `policy_would_deny`，脱敏副本使用 `redacted_proxy_decisions` 与 `redacted_proxy_gate_policy_actions`，不把离线计算写成实际阻断或已验证真阴性。

### 规则调整对检出的影响

本轮按本机真实 prompt 历史把门控误报率从 37.41% 压到 0.63%（过程见 [Hook 门控记录](codex-hook-gate.md)）。为确认这不是靠牺牲检出换来的，对同一批固定语料做了调整前后对照：银行卡类标注的行级拒绝数**完全不变**（Gretel 549/571、中文正式 752/862、中文聊天 333/504）；三套语料整体判定仅在 Gretel 上有小幅变化（`BLOCK` 1,170 → 1,154），唯一超过 2 个百分点的标注是 `device_identifier`（36.0% → 31.5%），来源正是被移除的伪银行卡命中。同期还修复了一处**真实漏检**：熵分析原先不扫 base64/hex 解码后的形式，`hex_encoded_secret` 对抗样本此前是靠伪银行卡命中偶然"拦住"的。

另以明确标注期望动作的合成夹具测试文本、PDF，以及真实 OOXML 结构的 DOCX、XLSX 和 PPTX。混淆矩阵：期望 `BLOCK` 的 13 项中，12 项返回 `BLOCK`，1 项返回 `ALLOW`；期望 `ALLOW` 的 9 项全部放行。漏检项是**仅保留含义、改写全部字面内容的内部文档**，四层词面/结构识别无法稳定抓到。未知二进制格式和无可提取文字的 PDF 均因无法完整检查而拒绝，这两项未算入内容识别检出率。

Office 夹具使用固定哈希的合成模板生成：DOCX 经 `python-docx 1.2.0`、XLSX 经 `openpyxl 3.1.5`、PPTX 经 `PptxGenJS 4.0.1` 建立；替换文本后分别用文档库重新打开，PPTX 还通过 Office 包结构校验。DOCX 模板移除了默认缩略图和自定义 XML，并同步删除相关关系；当前支持范围是**可提取文字、无嵌入媒体的文件**。媒体、缩略图或其他无法完整检查的部件仍按拒绝处理。这些各一份的合成 Office 文件证明了这三条具体解析路径，不能代替真实业务文件的兼容性测试。模板 SHA-256 在评测脚本中固定，ZIP 条目时间戳固定；两次全量复跑的判定、规则编号、样本哈希和语料计数一致，耗时字段因机器负载而变化。

前三套公开语料的汇总结果曾用于修正中文数字前的匹配边界，并补充身份证、银行卡和护照上下文规则；因此它们属于**开发诊断数据**，不能宣称为未见过的盲测集。公开语料的实体类型也不能直接映射成 `ALLOW/REVIEW/BLOCK` 真值：例如单独姓名、联系方式、证件号在不同策略和上下文下可能采取不同动作。

独立策略标签可以建立，但应先冻结检测器和企业策略，再从**未用于规则调整**的语料中按预先固定的种子抽样，纳入无敏感内容、边界样本和改写样本；标注者不看检测结果，分别给出期望动作与依据，对分歧进行复核并保留标签版本。完成后才能计算策略级混淆矩阵、敏感样本漏放率和良性样本误拒率。ai4privacy 留出集满足"未用于规则调整"这一条，但缺少独立策略标注，因此仍不是盲测标注集。当前报告里的合成夹具由开发者制作，虽有明确期望动作，也不构成独立盲测。源站零字节及 Agent 工具外发须另行验证。

## 密钥类语料的可得性

PII 有可直接下载并固定哈希的公开语料；**密钥类没有**。该方向当前的基准是 [SecretBench](https://arxiv.org/abs/2303.06729)（MSR 2023，97,479 条标注候选、其中 15,084 条真密钥，来自 818 个公开仓库），2025 年的 [Secret Breach Detection in Source Code with Large Language Models](https://arxiv.org/abs/2504.18784) 也在它的平衡子集上微调评测。但该数据集**不开放下载**：正文只提供元数据与 761 条正则，语料本体在 Google BigQuery 与 Cloud Storage，需联系作者并签署数据保护协议后按邮箱授权。因此本轮没有把它纳入评测，也不宣称在真实密钥语料上测过；`SECRET` 类的检出证据目前仅来自合成夹具与本机真实 prompt 历史上的命中。要补这一块，需要先走完该数据集的申请流程。

Agent 场景的隐私基准（PrivacyLens、AgentDAM 等）评的是 **Agent 在特定情境下该不该说**，判定依赖 LLM 裁判，与本引擎"对给定文本做内容识别"的任务不是同一个度量对象，本轮未纳入。
