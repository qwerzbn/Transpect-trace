# 固定版桌面后端的启动网络门闩设计

本文件定义后续在**隔离 Windows 虚拟机**中验证的 WFP 门闩。它尚未安装在当前用户的 Windows 桌面，也不是已完成的“每条 prompt”保护证明。现有 `desktop_guard_supervisor.py` 在后端启动后轮询发现进程，存在第一条请求早于 Native 就绪的空窗；在后端启动前已经生效的系统级网络规则或同步进程启动门闩才能封住该空窗。

## 固定身份与规则

- 管理员在启动 Codex 前，对固定 `codex.exe` 的规范化可执行路径和专用测试账户 SID 安装 WFP `ALE_AUTH_CONNECT_V4/V6` 持久默认拒绝。过滤条件同时包含 `FWPM_CONDITION_ALE_APP_ID` 与 `FWPM_CONDITION_ALE_USER_ID`；安装时读取后端映像 SHA-256，并固定当前桌面包 `26.1103.3517.0`、后端版本 `0.167.0-alpha.3.2` 与哈希 `40ecc3d8…`。`ALE_APP_ID` 是**路径**，不能当作 PID 或哈希证明。不同路径上的自动更新版本会绕过该规则，必须另行阻止自动更新或先配置新版本门闩。只按当前用户 SID 设置默认拒绝会影响该账户的其他程序，不适用于现用桌面。
- 持久拒绝应在独立子层中回读 GUID、层、条件、权重、动作、持久标志与启用状态；任一条件不符便不开放许可。不得删除或覆盖同名的未知 WFP 对象。
- Native 控制器完成固定包、父进程、SID、PID/创建时间、后端哈希、DLL 与实验报告准入，并收到 `native.ready` 和管道就绪后，才在**控制器拥有的动态 BFE 会话**添加比持久拒绝更高权重的临时许可。许可至少限定同一 SID、同一 `ALE_APP_ID`、TCP、目标地址与端口；正常 Codex 的动态目标地址需要单独验证。跨子层的普通 Permit 不能覆盖 Hard Block，必须在同一子层按权重排序并动态验证。
- 控制器退出或 BFE 会话结束时动态许可消失，持久拒绝仍在。主动停止时先删除许可、确认 WFP 状态，再释放 Native 租约；控制器异常退出时 BFE 清理动态会话作为兜底。过滤器增删会触发 ALE 流重新授权，但文档没有承诺“控制器失联后零字节”的即时界限，必须以真实 TCP/UDP 与 IPv4/IPv6 收件端实测。已存在的连接、代理代发、其他用户的进程，以及同一路径同 SID 的第二个进程仍是独立缺口。

## 与正常使用的冲突

默认拒绝会使用户在 Native 尚未就绪、版本不匹配、控制器故障或策略拒绝时看到网络错误。这是保证启动空窗没有未检查外发的代价。若为了维持 Codex 可用而在故障时自动放行，便不能声称每条 prompt 受保护。当前真实桌面已有三次用户可见故障，且第三次 `ValidationError` 的原始字段未留存；在隔离虚拟机完成前端和故障验收前，不应给现用账户安装门闩。

## 验收顺序

1. 在虚拟机中使用专用低权限账户与固定后端，确认持久规则先于 Codex 启动，并以本地非转发收件端验证未注入时 TCP/UDP、IPv4/IPv6 的目标正文为 0 字节；同时确认同机其他账户和其他应用不受影响。
2. 注入精确 Native DLL、确认管道/租约就绪后，只为本地测试目的地添加动态许可。正常请求须完成、捕获体 SHA 与源站实收 SHA 相同；敏感请求须在源站计为 0。对 HTTP/WSS、第一次请求、重复请求和大正文分别验证。
3. 强制结束控制器、管道和许可持有者，分别测量从故障到 WFP 重新拒绝的时延与窗口内收件字节数；有任何未检查正文到达就不能声明故障期间零字节。
4. 再启动同一路径同 SID 的第二个未注入后端，测试它是否共享动态许可。若共享，现有 `ALE_APP_ID` 规则不能作为单进程保护；需要独立进程网络身份或内核 callout。
5. 切换桌面包、替换后端文件、重用 PID，并分别确认许可拒绝；测试 Codex 常见登录、模型、插件和工具流程，记录默认拒绝对正常使用的实际影响。

只有这些验收及当前真实桌面的前端稳定性完成后，才考虑把门闩与自动发现器联动。WFP 能封住固定路径的网络启动空窗，无法单独看到 rustls 内的模型正文或证明 Native 已覆盖所有请求路径。
